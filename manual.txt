Introduction:
    Welcome to the Embrial programming language. Ebl for short. Ebl is a
    statically, typed low-level programming language, designed around an
    easy-to-read syntax that provides expressive, explicit, and memory-safe
    code. Embrial's type system controls data, through types, allocators,
    ownership and borrowing through references. Lang treats the command line
    interface, allocators, result types, optionals, and errors as first class
    citizens.  Embrial is intended to be used for both general and systems
    programming, favoring simple rules, predictable behavior, and a small set of
    composable primitives.

Source code representation:
    Source code is Unicode text encoded in UTF-8. Source code other than
    identifiers are not canonicalized meaning that a single accented code point
    is distinct from the same glyph constructed from combining the code point
    for the accent and the letter. Hence forth, a single Unicode code point will
    be referred to as a character. It is an error if the file is not valid
    UTF-8.

    The compiler may disallow the NULL character '\u000000' or may ignore
    '\u00FEFF' in the source text. The byte order mark will be removed if it is
    the first character of the source code.

    In Embrial identifiers are canonicalized using Unicode Normalization Form
    C, (NFC). Thus two identifiers are identical if their normalized forms are
    identical regardless of their original code point sequences.

Comments:
    Comments are used to document programs. Embrial programs are self
    documenting based on where comment occur. Embrial has a single form of
    comment, beginning with a hashtag '#', followed by an arbitrary sequence of
    characters, ending with a newline character '\n'.

    spec/comments.txt:
       1 |  # this is a comment

    Comments may occur only at the end of a line. Nested comments are impossible
    considering that every character between the first '#' on a line, until the
    newline at the end of the line is comment, meaning that any '#' enclosed in
    that region is a commented character.

    A block comment is considered to be 1 or more comments that are written
    sequentially with only whitespace between comments. Comments on sequential
    lines are logically --> [Quit Loop] by striping leading --> [Quit Loop] of every
    line of the block comment then --> [Quit Loop]. Bellow are two equivalent
    comments,

       2 |  # this is a 
       3 |      #    comment
       4 |  
       5 |  # this is a comment

    Note that the --> [Quit Loop] at the end of a comment is not trimmed. The first
    above comment ends with a single space character. Escape sequence are also
    processed,

       6 |  # comment with\na newline

    When printed would display as,
    comment with
    a newline

Memory model:
    Embrial uses an ownership and borrowing memory model to directly access
    memory while preserving memory safety. All data in Embrial has exactly one
    owner. When an owning value goes out of scope, the memory associated with
    the owned allocation is released. Embrial uses mostly copy semantics,
    reserving move semantics for assignments involving owned types, and mutable
    references.

    Borrowing using mutable or immutable references, allow data to be accessed
    without copying data, or moving ownership. The borrow checker prevents a
    whole class of memory-safety errors by enforcing 2 rules. First, a piece of
    data may have either one mutable reference or multiple immutable references
    borrowing from it, but not both at the same time. Secondly, a reference
    cannot outlive the data from which it is is borrowing.

    Embrial's memory model is designed around the pattern of copy semantics,
    while supporting move semantics where they are beneficial. The type system
    makes move semantics explicit for allocated types, and mutable references.
    Together, the type system and borrow checker can prevent invalid memory
    access, while allowing the compiler to determine when to safely release
    allocated memory.

Bindings:
    A binding is an association between a name and data. Bindings are either
    mutable or immutable. Mutable and immutable bindings are called variables,
    and constants respectively. To declare a binding, first write the mutability,
    followed by its type and name.

    spec/bindings.txt:
       1 |  var   x  i32; #   mutable binding
       2 |  const PI f64; # immutable binding

    Declaring variable and constants follow C-style scoping rules. Two bindings
    with the same name cannot be defined in the same scope.

       3 |  var x i32; # error: redeclaration of "x"

    A binding may be declared without being initialized. Any uninitialized
    binding is considered invalid until it assigned a value. Reading from an
    invalid binding is a compile-time error.

       4 |  println(x);  # error: "x"  is invalid
       5 |  println(PI); # error: "PI" is invalid

    After a binding has been initialized, if it is mutable, then it can be
    assigned a new value. Otherwise if a binding is immutable, then any
    additional assignments after the initialization will result in a
    compile-time error.

       6 |  x = 0; # "x" initialized
       7 |  x = 1; # "x" assigned a new value
       8 |  x = 2; # "x" assigned a new value
       9 |  
      10 |  PI = 3.1415926; # "PI" initialized
      11 |  PI = 3.14;      # error: constant binding "PI" allready initialized

    A binding can be declared and initialized in one line as follows,

      12 |  var y i32 = 3;

   
Reference types:
    Traditional pointer types have too many responsibilities. A pointer may own
    an allocation, borrow an object, permit mutation, permit reads, represent
    the absence of a value, or point to an array. Embrial divides these
    responsibilities into several unique types.

    Reference types are types whose values contain the address of another value.
    Embrial references are non-null and do not implicitly dereference their
    target. A reference is dereferenced explicitly using the .* operator. If a
    nullable reference is required, a reference can be combined with the
    optional type '?'. 

    No reference type can outlive the lifetime of the memory to which it refers.
    See [Life times] for more details. Brief, if an owning type has a longer
    life time then its allocator, or a borrow type has a longer life time then
    the binding from which it borrows, then it is invalidated after the shorter
    life time ends.

Owning types:
    Embrial uses the owning reference type '@T' to represent exclusive ownership
    of memory allocated for an instance of type 'T'. The owning type modifier
    '@' indicates that the binding owns the memory referenced by the address
    that the binding's value represents. A binding whose type is an owning type
    is referred to as an owning binding. When a valid owning binding goes out of
    scope, the owned memory is released.

    Below 'Heap.create<i32>(0)' is used to allocate an 'i32' on the heap and
    initialize it with the value '0'. See [Functions], [Modules], [Generics],
    and [Allocators] for more details.

    spec/ownedTypes.txt:
       1 |  const x @i32 = Heap.create(0);

    When an owning binding is assigned to another owning binding, ownership of
    the allocated memory is moved. Moving ownership first deallocates any memory
    owned by the target binding, then the reference contained in the source
    binding is copied to the target binding, lastly the source binding is
    invalidated. If the s The source binding must not be used until it is
    assigned a new value. A constant binding that has been invalidated cannot be
    assigned a new value.

       2 |  var y @i32 = x; 
       3 |  println(y);         # ownership error, x invalid after move
       4 |  x = Heap.create(1); # error, cannot assign twice to immutable 
            variable x
       5 |  y = Heap.create(2); # the memory allocated on line 1 is released

Non owning types:
    Non-owning references provide access to memory without transferring
    ownership of the referenced memory. In order to ensure that a value cannot
    be modified while simultaneously being read by another reference, Embrial
    separates non-owning reference into two mutually exclusive reference types,
    mutable references, and immutable references. At any given time, a binding's
    memory can either be borrowed by a single mutable reference or by multiple
    immutable references but not both at the same time.

Mutable references:
    To specify that binding's type is a mutable reference to a type 'T', use the
    mutable reference modifier '*' in prefix before type '*T'. As stated
    above a mutable reference does not own the underlying memory of the data it
    refers to. Instead it borrows access to the memory, and permits both reading
    and writing to the data through the mutable reference. To create a mutable
    reference to a binding x, use the get mutable reference operator '&' in
    prefix before the binding's name `&x`.

    spec/mutableReferences.txt:
       1 |  var x i32 = 0;
       2 |  
       3 |  var p1 *i32 = &x;
       4 |  var p2 *i32 = &x; # borrow error, p1 is already mutably borrowing x
       5 |  var r1 ~i32 = $x; # borrow error, p1 is already mutably borrowing x
       6 |  
       7 |  var p3 *i32 = p1; # p1 moved to p3
       8 |  var r2 ~i32 = p3; # cannot assign from mutable reference to 
            immutable reference
       9 |  
      10 |  x = 1; # borrow error
      11 |  p1.* = 2; # borrow error, p1 invalid after move of p1 to p3
      12 |  p3.* = 2;
      13 |  
      14 |  println(x); # borrow error
      15 |              # if p went out of scope on line 6, would print 2
      16 |  println(p1.*); # borrow error, p1 invalid after move of p1 to p3
      17 |  println(p2.*); # error, p2 is invalid
      18 |  println(p3.*); # prints 2

Immutable references:
    To specify that binding's type is an immutable reference to a type 'T', use
    the immutable reference modifier '~' in prefix before type '~T'. As stated
    above an immutable reference does not own the underlying memory of the data
    it refers to. Instead it borrows access to the memory, and permits both
    reading and writing to the data through the immutable reference. To create
    an mutable reference to a binding x, use the get immutable reference
    operator '$' in prefix before the binding's name `$x`.

    spec/immutableReferences.txt:
       1 |  var x i32 = 0;
       2 |  
       3 |  var r1 ~i32 = $x;
       4 |  var r2 ~i32 = $x; # multiple mutable borrows is fine
       5 |  var p1 *i32 = &x; # borrow error, r1 already immutably borrowing x
       6 |  
       7 |  var r3 ~i32 = r1; # copy r1 to r3
       8 |  var p2 *i32 = r1; # cannot assign from immutable reference to 
            mutable reference
       9 |  
      10 |  x = 1; # borrow error
      11 |  r1.* = 2; # error, cannot assign through dereference of immutable 
            borrow
      12 |  
      13 |  
      14 |  println(x); # borrow error
      15 |              # if r went out of scope on line 6, would print 0
      16 |  println(r1.*); # prints 0
      17 |  println(r2.*); # prints 0
      18 |  println(r3.*); # prints 0
