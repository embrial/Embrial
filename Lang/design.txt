     1. errors may occur on the same line
     2. the parser when parsing a statement imediatly recognizes that a type of

          - can only inform the user after the entire statement has been
            recognized. This may mean that the recognized statement has multiple
            lines. One or more of those lines may have allready been printed if
            they have errors in them in the naive approach.
     3. parsing has multiple stages meaning that the tree has to be traversed
        again meaning that errors appear out of order

      - desirable to avoid printing the same line multiple times to highlight

      - desirable to print errors in the top to bottom order as they appears in

    Storing errors, then sorting them when parsing finishes allows the second
    requirement to be achieved. It also decreases coupling meaning that the
    error formating technique can easily be switched in and out.

Parsing:
    Parsing has to iterate the AST atleast twice. This is due to the fact that
    modules, structs, interfaces, enums, and functions can defined after they
    are first used. Additionally everything that is included for a file is
    effectivly declared at the end of the file. Therefore type information has
    to collected and infered as much as possible during the first pass untill
    the relevant module, struct, interface, enum, and function fits the ussage
    contract of every previous ussage.

    main.lang
    |
    V
    Phase 1: semantic / type linking
    |
    |   toParse = [main.lang]
    |   parsed  = []
    |
    |   while toParse is not empty:
    |       file = pop(toParse)
    |
    |       phase1(file)
    |       # resolves all internal type restraints, type inference, and type
    |       # checking, resulting in a list of external type restraints
    |
    |       parsed.append(file)
    |
    |       for include in file.includes:
    |           if include not in parsed
    |              and include not in toParse:
    |               toParse.append(include)
    |
    V
    global symbol/type resolution constraints
    |
    |   # global semantic type resolution
    |   for file in parsed:
    |       file.verifyTypeRestraints(parsed)
    V
    Combined semantics model
    |
    V
    Phase 2: combined ir generation
    |
    V

    The AST preserves the structure of the source.

    struct Point {
        x i32;
        y i32;
    }

    const p Point = {.x = 32, .y = -10};

    becomes:

    STRUCT_DECL
        name: "Point"
        fields:
            FIELD_DECL
                name: "x"
                type: i32

            FIELD_DECL
                name: "y"
                type: i32

    CONST_DECL
        name: "p"
        type: Point
        initializer:
            STRUCT_LITERAL
                x → 32
                y → -10

    The AST doesn't need to answer "what does Point mean?" It just records that the source said Point.
    
language adds something C doesn't:

const p Point = {.x = 32, .y = -10};
const p1 Point = {.z = 42};


struct Point {
    x i32;
    y i32;
    z i32;
}

Before the struct declaration exists, you need somewhere to store:

Point:
    required fields:
        x → capable of 32
        y → capable of -10
        z → capable of 42

That is neither really AST nor ordinary symbol-table information.

I'd put it in a semantic/type object associated with the symbol:

Symbol
  │
  ├── name: Point
  ├── declaration: NULL
  │
  └── type → StructType
                │
                └── requirements
                     ├── x
                     ├── y
                     └── z

Then when the declaration appears:

Symbol
  │
  ├── declaration ─────→ AST_STRUCT_DECL
  │                         ├── x i32
  │                         ├── y i32
  │                         └── z i32
  │
  └── type ────────────→ StructType
                            ├── x → offset/type info
                            ├── y → offset/type info
                            └── z → offset/type info
So I'd use three layers
                    ┌──────────────┐
source ────────────→│     AST      │
                    │ what was said│
                    └──────┬───────┘
                           │
                           │ declaration
                           ▼
                    ┌──────────────┐
                    │    Symbol    │
                    │ what names   │
                    │ refer to     │
                    └──────┬───────┘
                           │
                           │ type
                           ▼
                    ┌──────────────┐
                    │     Type     │
                    │ what it means│
                    │ semantically │
                    └──────────────┘
    typedef struct {
        SourceLocation location;

        AstKind kind;

        size_t childIndex;
        size_t childCount;

        union {
            Literal *literal;
            TokenType operator;
        }
        
        Symbol *symbol;
        Type *type;
    } AstNode;
